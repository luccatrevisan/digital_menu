## 16/09/2026 - Handle serializer errors on the client-side
### Goal
Handle and display the address form validation errors returned by AddressSerializer (CEP, street, number, neighborhood, city, state, label) to the user during checkout.

### Implemented
- Changed the whole AddressSerializer removing all fields validation except the cep one, simplifying the ValidationError message and adding documentation
```python
class AddressSerializer(serializers.ModelSerializer):
    class Meta:
        model = Address
        fields = "__all__"
        read_only_fields = ["user"]

    def validate_cep(self, value):
        digits = "".join([c for c in str(value).strip() if c.isdecimal()])

        if len(digits) != 8:
            raise serializers.ValidationError("CEP inválido. Use apenas 8 dígitos e evite hífen (ex: 12345000).")

        try:
            cep_response = requests.get(VIA_CEP_URL + digits + "/json/", timeout=5)
            '''
            ViaCEP output: {
                                "cep": "01001000", -> only numbers, without hifen.
                                "uf": "SP"
                            }
            '''

        except requests.exceptions.Timeout:
            raise serializers.ValidationError("Não foi possível verificar o CEP. Tente novamente mais tarde.")
        
        except requests.exceptions.RequestException:
            raise serializers.ValidationError("Não foi possível verificar o CEP. Tente novamente.")

        data = cep_response.json()

        if data.get("erro"):
            # if there is a key "erro" in the API output, it means that the CEP doesn't exist.
            raise serializers.ValidationError("Esse CEP não existe. Confira o valor digitado.")

        if data.get("uf") != "RJ":
            # validation to avoid CEPs from places outside the delivery area
            raise serializers.ValidationError("Infelizmente não atendemos no seu estado ainda! Por enquanto nossa área de atuação está focada no RJ.")

        return digits
```

### Key Decisions
- **Why I decided to remove all the validations from the serializer:**
  I realized that there is no need to make a personalized validator message when the serializer already got the model rules. All fields except CEP had validators only to check if they were empty and, if they were sent empty by the user, the error message returned by the API would be from the Model before the system got to my custom message, since the address serializer is a ModelSerializer. It got the rules from the model that come from the blank=False and null=False attributes. I only kept the cep validation because its more specific to the business itself, since its an important code that reveals a true address.

- **What happened with the State Validation:**
  Unlike the other Address fields - except CEP -, the state field had more validations other than to check if it was empty. My initial approach was to use a text input from the user where they were supposed to WRITE their state but the state should be on the UF format, like "RJ" for Rio de Janeiro or "SP" for São Paulo. After some thought, I realized that this would make my user's life harder, and I should just use a selection of options for them. So, instead of making a validation to not only check if the field was empty but to also check if their input was only two letters, I just changed the model to accept a selection of choices (in this case, only one, because Chewie Cookies doesn't have a delivery area outside of Rio de Janeiro) and there was no need to check what the customer sent. If they created an address from another way, like from a terminal, which has really low chances of happening, the serializer would still get the model rules.

- **Why I kept the error handling on the client-side simpler:**
  One of the things that I like about backend engineering is error handling. It is something that could define a elegant way of communication between systems, like the frontend and the backend. Before, for the order creation error treatment, I used an elegant approach that would send both a message and a code for the client-side. I really like this because, the message has higher chances of changing than a code. The message always could be clearer or could have a typo. Using the specific code for that error could make the life of the frontend engineer easier. So, I tried to do this again for the address creation. Unfortunately, all the basic rules were set on the AddressModel and all messages would be coming from the model rules, not from my custom ValidationErrors. I think that there may be a way to place the custom errors - with messages and codes - in a higher priority than the model errors, but that would be unnecessary and maybe a lot of trouble just to show a similar message. I then realized that this approach could have better moments to use it other than others. Since I saw the necessity to use it on the order placement feature, I will revisit it soon to have a better understanding of the custom error handling and if there are specific moments to use it.
