## 19/08/2026 - Validate CEP
### Goal
Validate the user address input, starting on the CEP, using an external API to make sure it exists and return other values related to the CEP

### Implemented
- Improve the validation provided by copilot, checking first the users input
```python
  def validate_cep(self, value):
      '''normalize: accept numbers only and 8 digits (without hifen)'''

      digits = "".join([c for c in str(value).strip() if c.isdecimal()])

      if len(digits) != 8:
          raise serializers.ValidationError(
              detail={
                  "message": "CEP inválido. Use apenas 8 dígitos (ex: 12345000).",
                  "code": "invalid_cep"
              }
          )
```
 
- Then, still inside the validate_cep function, consumed the ViaCEP API
```python
  from requests import request
  VIA_CEP_URL = "https://viacep.com.br/ws/"

  def validate_cep(self, value):
    cep_response = request.get(VIA_CEP_URL + digits + "/json/")
    '''
    When a CEP with a valid format but nonexistent value is queried the response will contain an "erro" value equal to "true". This means the queried CEP was not found in the database.

    {
        "cep": "01001000",
        "logradouro": "Praça da Sé", -> equivalent to 'street'
        "bairro": "Sé", -> equivalent to 'neighbourhood'
        "localidade": "São Paulo", -> equivalent to 'city'
        "uf": "SP", -> equivalent to 'state'
    }
    '''

    if "erro" in cep_response:
        raise serializers.ValidationError(
            detail={
                "message" : "Esse CEP não existe. Confira o valor digitado.",
                "code" : "inexistent_cep"
            }
        )
      
    return digits
```
 
- And, to deal with blank inputs, I defined the cep field inside the serializer class

  class AddressSerializer(serializers.ModelSerializer):

### Key Decisions
- **How I chose ViaCEP API for the CEP validation:**
  I found three main options for the API: Correios API, Brasil API and ViaCEP. At first, I already removed the Correios API as a option because it requires a "pessoa jurídica" registry - which I have, I just don't need to deal with that kind of strict rules right now. Brasil API could be a good option since their terms of use are really simple and asks mainly to avoid requesting every single CEP from their database. also, their API returns JSON with the exact same names from my model fields, like "cep", "state", "city" and "neighbourhood". But, Brasil API does not appear to deal with the reverse way: searching for a CEP through other informations like state, city and street. So I decided to use ViaCEP, that, despite being in brazilian portuguese - getting away from the english pattern - allows to improve user experience for those that don't know their CEP number, asking for their "street", "city" and "state" to get its value.

- **Why use isdigit() instead of isnumeric() for the CEP user input validation?**
  Initially, github copilot created the function that I used as placeholder (check last devlog)using the isdigit() function. Since I didn't know about this function, I researched about python string methods and realized that copilot used this because its faster than isnumeric(). But, it is still prone to invalid input from the user. If I use isdecimal() I could have better results, since it checks if the string input character is a number from 0 to 9 and nothing more, while isdigit and isnumeric return true for numbers like ² and ¾.

- **Why I removed the object-level validation on the address serializer:**
  On the placeholder generated by copilot, it also created a function to check that the most important fields aren't empty. I chose to remove it because I would generate a generic error message for the user. For example, if I check multiple empty fields, it becomes hard to specify which one. And there are some fields that can be empty, like the complement field. So, if I build a validator for each field, the most important ones can have this "empty check" and the other ones, like complement, could just not have it, since not every address has a complement.

- **Why not just use "blank = False" and "null = False" on the address model?:**
  Because I don't want to show the user a generic message. The return would be something like "Este campo é obrigatório." ('This field is obligatory' in brazilian portuguese) and I feel that the chewie cookies' client needs to have more guidance than this. OBS.: This doesn't mean that I shouldn't use null=False and blank=False. I should just don't rely entirely on it and make validations on serializer level too (Check challenge 2 on the challenges section bellow)


### Challenges
1. **Should I place a request for the ViaCEP API on the frontend, the backend or even on both?**
   - **How I solved it:** I started by restraining the user of filling anything else than numbers. When I comes to the moment of filling the hifen (after the 5 digits), the frontend would to it automatically to avoid errors. But I realized that it is beyond my scope of knowledge and decided to focus my attention to error handling on the backend. If the user fills the CEP field incorretly, they will just not be able to create their address. Then I started thinking of other fields like street or city. I had experiences where I filled the CEP and other form fields would automatically be filled - what feels good, specially in a instant-delivery application where everything should be faster - and I think that this is a must-have. But, how can I do this with only one request?
   - **What I learned:** If I use the API to fill other address fields automatically, it should be on the frontend. In this case, would I be making two requests? One to fill the form - on the frontend - and other to check if the CEP exists - on the backend. I decided to leave this problem to the next step: Validating the street, city and state fields - that are directly associated with the CEP.

2. **How should I make the 'empty_field' validator?**
  - Since I want to personalize the error message to the user and to keep all error handling code consistent (similar), I had some problems dealing with the case of CEP being empty.
  - As you probably already know, I decided to remove the object-level validation that checked if some of the address fields are empty because of the model rules. There was no need for a not-empty validator for multiple fields. The benefit of having a personalized validator is to have a personalized error message - that is clearer and more objective than a generic one.
  - If I use `null=False` on the model field, creating a serializer validation only to check if the field is empty is redundant because the serializer knows the model rules when validating the input.
  - But, I initially thought of removing the `null=False` attributes on models.py so that I could do the validation myself. Then realized that isn't good pratice. If I create something via admin - which is absolutely possible - or even via python console, the serializer validators wouldn't apply. I even went an "extra mile" and thought about someone hacking the system creating an infinite amount of invalid addresses. The anxiety (or spider sense) went crazy here maybe.
  - Then, centralizing the validation on the serializer would only work via HTTP request - the only way that goes through the serializer. 
  - So, for this one, I asked help to google gemini to have a better understanding of what I could do, since its a really specific problem.
  - This was the provided solution, using extra_kwargs:
  ```python
    class AddressSerializer(serializers.ModelSerializer):
    class Meta:
        model = Address
        fields = "__all__"
        read_only_fields = ["user"]
        extra_kwargs = {
                    'cep': {
                        'error_messages': {
                            'max_length' : 'Preencha somente 8 números.
                            'required': 'CEP é obrigatório.',
                            'null': 'CEP é obrigatório.',
                            'blank': 'CEP é obrigatório.'
                        }
                    }
                }
  ```
  - Since I couldn't find much documentation about extra_kwargs and this would look terrible if I used this approach for every address field, I decided to ask chatgpt for another approach and got this:
  ```python
    class AddressSerializer(serializers.ModelSerializer):
    cep = serializers.CharField(
        required=True, 
        error_messages={
            "required" : {
                "message" : "O CEP é obrigatório.",
                "code"  : "missing_cep"
            },
            "blank" : {
                "message" : "O CEP não pode estar vazio.",
                "code"  : "empty_cep"
            }
        })
  ```
  - This looks a lot more organized, since the field has its own parameters. If I used the other way, it would be a long ass dictionary. With enough time, it would be confusing.
