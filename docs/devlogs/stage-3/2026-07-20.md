## 20/07/2026 - Simplify order flow and error handling
### Goal
Simplify the order creation flow by removing business rules that are not required for the current MVP. The main objective is to allow authenticated users to place orders successfully while making the validation flow easier to understand and maintain.

### Implemented
- Removed unnecessary code from orders.models
```python
class Order(models.Model):
    # removed the statuses

    # removed the delivery type

    total_price = models.DecimalField(max_digits=10, decimal_places=2, default=0)
    created_at = models.DateTimeField(auto_now_add=True)
    user = models.ForeignKey(CustomUser, on_delete=models.PROTECT, null=False, blank=False)
    address = models.ForeignKey(Address, on_delete=models.PROTECT, related_name="orders", null=True, blank=True)
    # removed address snapshot

    def update_total_price(self):
        total = sum(item.subtotal for item in self.items.all())
        self.total_price = total
        self.save(update_fields=["total_price"])

    # instead of using order state machine to make the validations, I now only need to validate minimum price
    def validate_minimum_price(self):
        if self.total_price < 30:
            raise ValidationError("The total price should be R$30,00 or more.")

    def __str__(self):
        return f"Order #{self.id}"
```
 
- Improved services.create_order
```python
def create_order(user, items_data):
    with transaction.atomic():
        order = Order.objects.create(
            user = user
        )

        for item in items_data:
            menu_item_id = item.get("menu_item_id")
            quantity = item.get("quantity")

            menu_item = MenuItem.objects.get(pk=menu_item_id)
            stock = Stock.objects.select_for_update().get(menu_item=menu_item)
        
            # decreases stock
            if stock.quantity is not None:
                stock.quantity -= quantity
                stock.save(update_fields=["quantity"])

            
            # create order item
            OrderItem.objects.create(
                order=order,
                menu_item=menu_item,
                quantity=quantity
            )

        # update total order price
        order.update_total_price()
        order.validate_minimum_price()

        return order
```
 
- Improved orders.serializers
```python
class OrderCreateSerializer(serializers.Serializer):
    items = OrderItemInputSerializer(many=True)
    
    def validate_items(self, items):
      # now I have an early check on empty carts, instead of checking it after the whole logic.
        if not items:
            raise serializers.ValidationError("The cart cannot be empty.")

        for item in items:
            try:
                menu_item = MenuItem.objects.get(pk=item["menu_item_id"])

                if not menu_item.is_available:
                    raise serializers.ValidationError(f"{menu_item.name} is not available.")
                
            except MenuItem.DoesNotExist:
                raise serializers.ValidationError(f"Menu item {item['menu_item_id']} does not exist.")

            try:
                stock = Stock.objects.get(menu_item=menu_item)
            
                if stock.quantity < item["quantity"]:
                    raise serializers.ValidationError(f"Only {stock.quantity} units available.")
            
            except Stock.DoesNotExist:
                pass # because the stock not existing doesn't mean that the item is not available. it just means that the item has unlimited stock

        return items
```
 
### Key Decisions
- **Why I chose to remove the Order State Machine:**
  There is no use for it right now. I am trying to have a simpler approach for the moment and it adds unnecessary complexity. I am first trying to understand how I can make the logic and the flow to place an order with good error treatment. The statuses were getting on my way to make an organized codebase. That doesn't mean that the Order State Machine is a bad feature. I intend to improve the project in the future using it so that I can show the client the status of their order. But for now I am searching for a MVP. The goal is to just make the menu able to proccess an order made by a real user, independently of their experience - at least for now.

- **Why I chose to remove the Delivery Type:**
  Before, to confirm an order, I had 4 steps: Check if there is any item in the payload, check the minimum price, check the delivery type and, if its delivery type - not pickup -, check the address. I realized that it may be doing many things when the project should be simpler. I started thinking like I was developing a MVP. So, for example, a few months ago the company started selling cookies on a delivery app and they only had the delivery option. Only recently, a few weeks ago, they started accepting pickups on each store. I figured I could do the same and focus on the core functionalities instead of these specific features. This makes all validations related to delivery type irrelevant, so I removed them.

- **Should I use address related to an order AND to an user?**
  Yes. I should relate address with user mainly for UX. What I am planning is: After clicking the checkout button, the user will be redirected to a page where they are going to fill the delivery form with address but only if they didn't have filled it before. If they did, there will be address options (based on how many addresses they have filled) to choose. And the address relationship to order is because the company have a smaller area of operations. Chewie Cookies is an ecommerce, but is not Amazon. I can't even delivery to the whole country. I can delivery only up to 5km from the store, rarely I can deliver to more distant addresses. So, I would like to have the order addresses history so that I could invest in ads, for example, to the places/neighbourhoods that have the most orders. This way I can avoid spending ads in areas that would not give so much financial return. 

- **Why I chose to remove the address snapshot from the Order model:**
  I think there is no need for them. I have accessed the Amazon ecommerce website and started placing an order to get an idea of what a professional order placement flow would be like. When I got to the address page, I had to choose between the ones that I had registered and couldn't remove any of them. I decided to use Amazon's UX as inspiration for my project. So, it means that I don't really need the snapshot and that I should use on_delete=PROTECT. I decided that addresses will be immutable once used for an order. If a user wants to modify an address, the application creates a new Address instance instead of updating the existing one. This way I won't have problems with deletion in the future.

### Challenges
1. Where should inventory mutations happen: the serializer or the service layer?
   - **How I solved it:** I like the idea of building the serializer with only a simpler responsability: Checking only if the stock quantity is lower than the order quantity. 
   - **What I learned:** The responsability to **change** the actual stock quantity, should come from the create_order service because of the atomic transaction. This way, I can avoid race condition in stock decreasing.
